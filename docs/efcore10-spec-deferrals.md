# EF Core 10 specification coverage and deferrals

Status: this ledger is audited against the revision that contains it, which is the EF Core 10 provider
change reviewed on top of the implementation branch tip `7ae12133607763c2431f7e8b7957783b3ef53275`,
with the fixed skip-inventory baseline `14c2cd558e37c71e7a2fca75e339ef902effdf60`. Only the
skip-inventory baseline is pinned: the ledger describes the revision it is committed with, not a
historical passing state of the branch.

This ledger is the public record for the EF Core 10 specification suites that the provider does not
subclass yet and for the method-level deferrals introduced while the EF Core 10 provider work was
reconciled. It is intentionally separate from the provider's historical skip inventory. Existing
Pomelo 9 coverage remains enabled; an EF Core 10 base is listed here only when the corresponding split
suite is not run by a concrete Pomelo test class.

The audit is executable from any working directory:

```text
test/EFCore.MySql.FunctionalTests/audit-efcore10-spec-coverage.sh
```

The check uses the immutable main baseline `14c2cd558e37c71e7a2fca75e339ef902effdf60`, so it detects
newly introduced method-level skips without sweeping the repository's historical skips. The table
records all 39 EF Core 10 base ignores and the 14 method-level skip additions relative to that
baseline. Every entry has one of four classifications:

- `database-native`: a server or connector limitation is the reason for the deferral and the evidence
  names the capability.
- `upstream issue`: behavior is tracked by an EF Core issue.
- `historically unsupported`: the provider has not exposed this workflow in a supported release and the
  history is part of the reason for retaining the deferral.
- `explicit follow-up`: provider work or a dedicated EF Core 10 test slice is still required; the
  reference is the stable follow-up identifier.

## Evidence rules

Every row carries two machine-checked evidence fields:

- `coverage=` names the provider tests that the audit resolves inside this repository, using the form
  `test/<path>.cs#<Type|Method>`, with several references separated by commas. `coverage=none` is
  allowed for a behavior area without any provider test, and then the deferral has to state that the
  area is uncovered. The audit fails when a referenced file or member does not exist, so a row cannot
  cite a test that is not there.
- `deferred=` states what the EF Core 10 suite still leaves unverified for this provider and repeats
  the follow-up identifier of the row. Where the suite is small, the field names the upstream test
  count and representative test methods. The audit rejects empty deferrals and vague wording such as
  "needs reconciliation" or "where supported", and rejects two rows that share the same deferral
  wording, so a row cannot be closed by rephrasing.

`coverage` is not an equivalence claim. It names the tests that exercise the same provider behavior
area today, and the deferred delta names what is not covered by them. The EF Core 10 translation and
type suites are a reorganization of translation tests that the provider already ran in earlier shared
suites, so their rows are verified-gap entries for pre-existing behavior: they name the concrete
provider test methods that assert part of that behavior and state which expectations stay unverified
until the split suite is subclassed. Suite reorganization does not turn pre-existing arithmetic,
string, date or type behavior into a new EF Core 10 capability, and those rows therefore do not defer
that behavior as a new feature under ADR 0004. Rows whose delta is a genuinely new EF Core 10
capability (complex-type JSON associations, complex-type collections in JSON, primitive collections
inside JSON documents) defer that capability under ADR 0004 instead of claiming equivalent coverage;
where only a slice of such a capability is missing, the row names both the covered slice and the
unverified slice instead of claiming that the provider implements none of it. Rows where an EF Core 10
suite reuses the test methods of an association suite the provider already runs say so explicitly and
name the remaining storage-specific delta.

`coverage=` is the test evidence of the revision that contains this ledger, not historical passing
equivalence. Several owned-JSON rows therefore cite regression tests that this EF Core 10 change added
(`Owned_json_nested_members_are_persisted_and_reload_with_a_new_context`,
`Owned_json_collection_elements_are_persisted_and_reload_with_a_new_context`,
`Owned_json_null_and_root_members_keep_json_semantics`,
`Owned_json_member_paths_stay_unambiguous_when_a_property_name_matches_a_nested_path`): those tests
verify the owned-JSON fragment and JSON member path fixes that this change introduced, and
the behavior they assert did not pass at the starting tip `7ae12133607763c2431f7e8b7957783b3ef53275`.
The other references are tests that already existed and keep passing unchanged.

The EF Core 10 suite scope in `deferred=` (test counts and method names) was read from the EF Core
`v10.0.0` specification test sources, which are the sources of the `10.0.0` specification test packages
this repository compiles against. The suite layout of EF Core 10 is a reorganization: several suites
forward to the shared association bases (`Associations*TestBase`, `OwnedNavigations*TestBase`,
`ComplexProperties*TestBase`) with a different fixture, which is why the provider can already run the
same test methods for the navigations, owned-navigations and table-splitting relation kinds.
